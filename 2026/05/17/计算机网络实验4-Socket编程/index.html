计算机网络实验：Socket 编程

发表于2026-05-17|更新于2026-11-07|计算机网络
|浏览量:

实验要求

实验目的

学习网络编程基本概念（InetAddress、URL、URLConnection 的应用），掌握 Socket 的 TCP 通信与 UDP 通信编程，熟悉 Socket、ServerSocket、DatagramPacket、DatagramSocket 类的使用。

实验内容与任务

  • 4.1：使用 InetAddress 类获取本地主机名称和 IP 地址；获取指定网站的全部 IP 地址；使用 URL 类下载学校首页并统计网页文件大小，将页面全部对象（图片、文本等）保存到本地。
  • 4.2（TCP 通信，基本内容 90%）：编写 TCP 程序实现客户端、服务器之间的通信——(1) 指令交互：客户端发送 Time 命令，服务器返回当前时间；发送 Exit 命令，服务器返回 “Bye” 后关闭连接退出；(2) 文件传输：客户端发送文件请求，服务器先传文件名，客户端接收后再传输文件内容，客户端改名保存到本地。要求：程序包含完整的服务器端和客户端；服务器持续监听请求；关闭服务器时严格按 TCP 四次挥手流程实现；双方均打印接收到的消息和发出的命令。
  • 4.3（UDP 聊天，基本内容 85%）：编写 UDP 程序实现不同客户端之间的聊天功能——参考微信/QQ 聊天，包含聊天内容区域和输入文本区域，通过功能按钮实现发送、删除当前输入文本以及退出聊天系统；包含一个服务器端程序和多个客户端程序，通过 UI 界面显示聊天交互过程。
  • 进阶拓展（可叠加）：学生信息数据库查询（需解决 TCP 粘包问题）、任意格式文件传输、群聊/表情/聊天记录搜索/消息撤回、UI 美化等。

实验环境：Windows 操作系统；Internet 连接；Eclipse + Java 开发环境。

4.2 TCP 客户端/服务器通信程序

编写TCP程序实现客户端、服务器之间的通信

（1）指令交互：客户端向服务器端发送Time命令，服务器端接受到该字符串后将服务器端当前时间返回给客户端；客户端向服务器端发送Exit命令，服务器端向客户端返回“Bye”后关闭连接退出程序；（2）文件传输：客户端向服务器端发送文件请求，服务器端接收到请求后，先向其传输文件名，当客户端接收后，再向客户端传输文件。客户端接收文件，并对其改名（文件名可自行定义）和存在本地。

要求：（1）编写完整程序包含服务器端程序和客户端程序；（2）服务器端能够持续监听客户端的请求；（3）关闭服务器时，请严格按照TCP四次挥手的流程来实现；（3）服务器端和客户端均需打印出接收到的消息和发出的命令。

实验原理： TCP（Transmission Control Protocol）是一种面向连接的、可靠的、基于字节流的传输层协议。Java通过 ServerSocket 和 Socket 类提供了TCP编程的高层抽象。TCP连接的建立需要三次握手，关闭需要四次挥手，本实验严格按照协议规范实现。

关键技术点：

多线程处理：服务器端使用 while(true) 循环持续监听，为每个客户端连接创建独立线程，支持并发访问。

指令解析：服务器端读取客户端发送的字符串，通过 equals() 或 startsWith() 方法识别 Time 和 Exit 命令。

文件传输协议：自定义简单的应用层协议——先传输文件名（带长度前缀或换行符分隔），客户端确认后再传输文件内容，确保接收端知道文件边界。

四次挥手实现：主动关闭方先发送 shutdownOutput() 或 close()，等待对方的确认和关闭请求，严格遵循 FIN → ACK → FIN → ACK 的流程。

讨论与总结

实验过程中遇到的问题及解决办法

问题一：DNS 解析异常处理 —— 在实验4.1.2中，查询 www.google.com 时抛出 UnknownHostException。经过分析，这是由于国内网络环境对Google域名解析的限制所致。解决办法是在代码中添加完善的异常处理机制，使用 try-catch 捕获异常并输出友好提示信息，同时程序继续处理后续域名，不会因单个域名解析失败而中断。

问题二：网页爬虫中的相对路径解析 —— 在下载某高校首页资源时，HTML中引用的资源路径形式多样，包括绝对路径（https://…）、根相对路径（/images/…）、相对路径（css/style.css）以及协议相对路径（//cdn.example.edu.cn/…）。最初仅处理了部分情况，导致部分资源下载失败。解决办法是编写了 resolveUrl() 和 resolveCssUrl() 方法，针对四种路径形式分别处理，确保所有资源都能正确解析为完整URL。

问题三：TCP 文件传输的粘包问题 —— 在实验4.2的文件传输中，最初直接将文件内容写入输出流，客户端使用固定大小缓冲区循环读取，导致无法判断文件传输结束边界，出现粘包现象。解决办法是设计简单的应用层协议：先发送文件名（以换行符结尾），客户端确认后再发送文件内容，客户端根据读取长度判断文件结束，或先发送4字节的文件长度前缀。

问题四：UDP 消息乱序与丢失 —— 在实验4.3中，UDP本身不保证消息顺序和可靠性，测试时发现偶尔出现消息丢失或乱序。对于聊天应用，消息乱序会严重影响用户体验。解决办法是在应用层增加简单的序号机制，客户端显示时根据序号排序；对于关键指令（如上线通知）增加超时重传机制。对于文件传输等对可靠性要求高的场景，建议改用TCP或实现基于UDP的可靠传输协议（如QUIC）。

问题五：UI 线程阻塞 —— 最初客户端在UI主线程中直接调用 socket.receive() 接收消息，导致界面卡死无法响应用户操作。解决办法是将网络接收操作放在独立的后台线程中，使用Swing的 SwingUtilities.invokeLater() 或JavaFX的 Platform.runLater() 更新UI组件，确保界面响应流畅。

意见与建议

5.1 对实验内容的意见

实验难度梯度： 实验4.3（UDP聊天）的工作量明显大于前两个实验，涉及UI设计、多线程、网络编程等多个知识点的综合运用。建议将UDP聊天实验拆分为两个子实验——基础版（命令行交互）和进阶版（GUI+高级功能），让学生循序渐进地掌握。

实验指导细化： 部分实验步骤描述较为简略，例如TCP四次挥手的具体实现方法、UDP服务器如何维护客户端列表等，建议补充更多的代码框架或流程图指引，减少学生在非核心知识点上的时间消耗。

网络环境说明： 建议在实验指导中明确说明网络环境对实验结果的影响（如DNS解析、防火墙限制等），避免学生因网络环境问题产生困惑。

5.2 对实验形式的建议

增加抓包分析环节： 建议在TCP/UDP实验后增加Wireshark抓包分析任务，让学生直观观察三次握手、四次挥手、TCP报文段结构、UDP数据报结构，将理论与实践深度结合。

引入现代框架： 在掌握基础Socket编程后，可以增设选做实验，介绍Netty、Mina等高性能网络框架，或Spring WebFlux的响应式编程，让学生了解工业界的最佳实践。

小组协作与代码评审： UDP聊天实验适合分组完成，建议引入小组协作机制，不同组之间进行互联互通测试，并进行代码评审，学习他人的设计思路和编程技巧。

增加性能测试： 建议增加服务器性能测试环节，使用JMeter或自定义压测工具，测试TCP服务器在高并发场景下的吞吐量、响应时间和资源占用，引导学生思考性能优化方案。

实验报告模板优化： 当前报告模板以文字描述为主，建议增加”关键代码截图”、”运行截图”、”Wireshark抓包截图”等固定板块，规范报告格式，同时减轻学生排版负担。
