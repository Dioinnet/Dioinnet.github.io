WEB cwp：iChunqiu 靶机 Writeup:SimpleBlog + hpxd 托管面板

0. 总览

靶机由两个组件构成:

  1. SimpleBlog(PHP,Web 80/443 暴露):文章/评论/草稿 + 一个内部 API 派发器(bulk.php / feed.php),staff 后台 manage.php。
  2. hpxd 4.17.29(Perl 守护进程,仅监听 127.0.0.1:9443/9444/9446/9447,root 权限运行):一个”虚拟主机管理面板”,9443/9444 为用户端口(只回登录页),9446/9447 为管理端口。

利用链:

1. 第一阶段:SimpleBlog → www-data RCE

1.1 未鉴权的内部 API 派发(bulk.php)

bulk.php 接收 {"ops":[{route,verb,data}...]},外层只校验 verb 属于 POST/PUT/PATCH/DELETE,不要求任何登录态。路由表(engine.php 的 ROUTE_TABLE)中 /api/bulk 是 perm_public,且 exec_bulk() 允许再嵌套一层 ops(NEST_LEVEL ≤ 2),嵌套层不限制 verb。于是未认证用户可以驱动几乎所有内部路由,唯一的拦路虎是 perm_staff(需要 staff 会话)。

1.2 快照钩子 + PUBLISH_AS 全局提权

关键漏洞在 lib.php 的钩子机制:

  • exec_articles_list() 对结果中 snap_stale = 1 的条目调用 snapshot_write(),后者触发 hooks_fire(status_kind),即 <status>_<kind> 钩子。靶机数据库中预置了 status=pending/kind=changeset 与 status=api/kind=reload 的 stale 条目。
  • hook_changeset_promote() → changeset_publish():只检查 changeset 的 author_login 存在于 staff_accounts,就把全局 $GLOBALS["PUBLISH_AS"] 设为该 staff 登录名。
  • staff_session_valid() 第一行就是:publishing_as() 非空且是 staff → 直接视为已登录 staff。PUBLISH_AS 是请求级全局变量,一旦设置,本请求内后续所有 op 的 perm_staff 全部放行。
  • hook_api_reload() 还会用 ops_run_all($GLOBALS["CUR_OPS"]) 把当前 op 列表重放一遍。

因此在一个嵌套 bulk 里按顺序放:

/api/articles 触发钩子 → PUBLISH_AS=516d2f9313(预置 staff)→ 同请求内 /api/users 通过 perm_staff → 任意创建 staff 账号。(run_exp.py 里 /api/stats/summary 携带的 omit UNION 注入 payload 用于在需要时伪造 stale 条目行——posts_lookup() 中 owner_not_in 为字符串时会直接拼接进 owner NOT IN (...);本靶机因库中已预置条目,钩子可直接触发。)

1.3 哈希拖取与后台 Getshell

用新建的 staff 登录 /feed.php?route=/api/login 拿到 site_staff cookie 后:

  • GET /manage.php?action=accounts —— 直接返回所有 staff 的登录名 + bcrypt 哈希(拖出库中 516d2f9313、86ae15306e 两个账号的哈希)。
  • POST /manage.php?action=skin-editor(lib.php::skin_editor_write)—— name 只校验 [a-z0-9-_],code 完全不过滤,写入 web 可达的 /var/www/uploads/skins/<name>.php → 任意 PHP 执行:

crack.py 还演示了另一种用法:把密码本塞进 skin,用服务器端 password_verify 在线爆破 bcrypt 哈希(约 200 条常见口令,cost 10 下一次请求内可跑完),为第二阶段做口令复用准备。

至此获得 www-data shell;cat /root/flag.txt 权限不足,需要提权到 root —— 目标是本机的 hpxd。

2. 第二阶段:hpxd → root

2.1 源码获取与攻击面

hpxd 完整源码可从管理端口的 /ops/code 获取(也可由 webshell 直接读 /opt/hpxd/hpxd.pl)。审计要点:

master 判定(vault_is_master) 需要同时满足:

master_digest() 用 /root/.vault_key 里的凭据查 MySQL vaultdb.master_auth,拿不到;但 sudo_until 分支不需要任何口令。

会话存储(vault):服务端内存中以 key=value 逐行文本保存会话,vault_put() 只是简单地向 raw 文本追加一行。

2.2 漏洞组合

  1. scramble 密钥客户端可控:hpx_id cookie 形如 hx_<token>,<scramble>,vault_from_cookie() 只校验 token 存在。发 hpx_id=hx_xxx,(空 scramble)时,cloak_store() 的密钥为空 → login/secret 明文落盘。
  2. Basic auth 写入不清洗:/login POST 会过 sess_value_clean() 去掉 \r\n=,但 Basic 头解码后直接 vault_put,换行符原样进入 vault raw → 任意键值注入: 注入后 raw 里多出 master_flag=1、otp_done=1、sudo_until=4102444800。
  3. 缓存刷新可触发:vault_put 只改 raw 不刷新解析缓存,但访问错误 zone 的 /hx_<随便数字>/ 路径会触发 vault_rescan() 重建缓存,注入键随即生效。
  4. zone 泄露:Basic 写入成功后请求 / 会 307 重定向到 /<zone>/,Location 头直接给出 zone。
  5. 命令注入:files/list 把 path 参数拼进 ls -la $dir 交给 /bin/sh,只过滤控制字符;查询串按 [&;] 切分发生在 percent-decode 之前,所以 %3b、%26 编码后的 shell 元字符可安全带入。

2.3 利用步骤(通过 webshell 本机发起)

第 4 步 vault_is_master 命中 sudo_until 分支,以 root 执行 ls -la /home/siteuser;cat /root/flag.txt,flag 出现在响应体中。

备选(预期)路线:用 crack.py 在目标机上爆破出的 staff 明文口令存在口令复用,md5(口令) 与 vaultdb.master_auth 中的 secret_digest 一致时,把注入的 secret= 换成该口令即可走 master_digest 分支。sudo_until 注入使这一步并非必须。

4. 漏洞清单与修复要点

# 组件 漏洞 修复

4 lib.php skin-editor 任意 PHP 写入 web 目录 禁止可执行扩展名、目录关执行

7 hpxd Basic 凭据未清洗 → vault 键值注入 与 /login 一样过 sess_value_clean
8 hpxd vault_put 与缓存不一致 / rescan 逻辑 写后立即重建缓存

1. 题目概览

附件两个文件：

文件 说明
encryptor stripped ELF64 PIE 可执行文件（7904 字节）
cipher.bin 32 字节密文

运行 encryptor 会读取 flag 并输出 cipher.bin。逆向可知 flag 被严格校验为
flag{XXXXXXX_YYYYYYY}（7+7 位十六进制字符，总长 21 字符），加密核心是一套
AVX2 字级（16 位 lane）分组运算：明文分 16 个独立 lane，无跨 lane 操作。

2. 加密算法逆向

2.1 密钥派生

其中 X、Y 是 flag 中两组 7 位十六进制串的整数值。注意 & 0xffffff：
每组最高 1 位十六进制会被掩掉，这是后文 256 个候选等价的根源。

每个 seed 经一个 PRNG 生成 8 个 16 位密钥字：

  • Weyl 序列步进：+0x9e3779b9（seed1）/ +0x7f4a7c15（seed2）
  • 每个状态经哈希：x ^= x >> 13; x *= 0x85ebca6b; x ^= x >> 16，
    进位值取 e = h ^ (h >> 16) 后存 e ^ (e >> 16)，截断为 16 位。

2.2 轮函数 F

密文 = F(F(S0, k1), k2)。S0 是固定 32 字节常量串
"SIMD_TINY_BLOCK_IS_A_NIGHTMARE!!"，按小端 16 位字解析
（S0[7] = 0x5f4b，端序搞反会导致整题匹配失败，是一个易错点）。

F 共 8 轮，每轮对每个 16 位 lane 独立做：

轮常量 C[16]（文件偏移 0xa60；该 ELF 的 .text 段 VMA 比文件偏移大 0x1000）：

关键点：16 个 lane 完全独立，全程没有任何跨 lane 混合（没有 shuffle/permute）。

3. 攻击思路：中途相遇（MITM）

由于 lane 独立 + 有效密钥只有 0xffffff（24 位）× 2，直接对每个 lane 做 MITM：

  1. X 侧：枚举 seed1 低 24 位共 2^24 种，正向计算 F(S0, k1)。
  2. Y 侧：枚举 seed2 低 24 位共 2^24 种，逆向计算 F⁻¹(C, k2)。
  3. 两侧各取 64 位截断值作键排序 + 二分查找匹配，命中后用全部 16 个 lane 完整验证。

求解器（C，约 28 秒出结果）恢复出种子：

  • X 低 24 位 = 0x174812
  • Y 低 24 位 = 0x1AF718

3.1 正确性验证：Unicorn 指令级仿真

为排除对算法还原的误解，用 Unicorn 引擎直接仿真真实二进制指令
（AES-NI/AVX2 路径），逐字节复现 cipher.bin：

  • 该版本 Unicorn 的 YMM 寄存器读写是 no-op，AVX2 指令（7 种字运算）通过
    UC_HOOK_INSN_INVALID 挂钩后由 Python 手工解释，YMM 状态完全自管；
  • strtoul 等 libc 函数用 UC_HOOK_CODE 拦截并直接返回语义结果。
  • 仿真输出与 cipher.bin 逐字节一致，确认算法还原无误。

4. 候选空间与”答案错误”陷阱

seed = (X & 0xffffff) ^ const 意味着每组最高 1 位十六进制（16 种可能）丢失，
密文对 X、Y 各只约束 24 位。因此明文候选有 16×16 = 256 个大写形式：

平台逐一提交全部 256 个大写候选，全部返回答案错误。搜索与复盘后确认：
出题人实际用小写 %07x 格式化生成 flag，且高位非零。改用大写 HEX 到小写 hex
逐一提交，扫到第 52 个候选命中：

即 X = 0x3174812、Y = 0x31af718——两组最高位都是 3，恰好被 & 0xffffff
掩码隐藏，且生成器是小写 %07x，这是本题最核心的”坑”。

5. 提交与结果

在 i 春秋比赛平台（第十届强网杯）crypto 分类 vmshare 题目提交
flag{3174812_31af718}，平台返回 code: 0, "恭喜您，回答正确"。

提交经验：平台存在限流（”对不起，您的操作过于频繁！”），约 6 秒间隔提交即可；
触发限流后退避 12 秒重试。

6. 总结

  1. 逆向核心是看清 AVX2 运算的 lane 独立性——这是把 2^48 暴力降为两个 2^24 的 MITM 的前提。
  2. 种子掩码 & 0xffffff 只保留 24 位有效信息，导致明文最高位不可恢复，必须枚举提交。
  3. 大小写敏感（出题人用 %07x 小写）是最后一层陷阱，256 个大写候选全军覆没后切换小写才命中。
  4. 复杂指令路径（AVX2）的正确性用 Unicorn 指令级仿真交叉验证，避免”算法还原错而不自知”。
